
바운디드 컨텍스트 맵(Bounded Context Map)은 복잡한 시스템 내에서 서로 다른 도메인 모델이 적용되는 경계를 명확히 정의하고, 이들 간의 관계를 시각적으로 표현한 맵입니다. 이 맵은 시스템 내에서 도메인의 경계를 구분하고, 각각의 컨텍스트가 어떻게 상호작용 하는지를 이해하는 데 도움을 줍니다. 바운디드 컨텍스트는 특정 도메인 모델이 적용되는 경계 내의 모델링 영역을 의미하며, 이를 통해 복잡성을 관리하고 모델의 정확성을 유지할 수 있습니다. 도메인과 도메인의 경계를 모델링하는 것으로 이는 [마이크로 서비스 아키텍쳐(Micro Service Architecture. MSA)](https://en.wikipedia.org/wiki/Microservices)를 개발 할 시에 서비스 단위 기준이 될 수 있습니다. 
바운디드 컨텍스트 맵은 시스템의 전체 구조를 이해하고, 각 컨텍스트 간의 의존성과 통신 방식을 명확히 하는 데 중요한 역할을 합니다. 이는 팀이 보다 효율적으로 협업할 수 있게 하며, 시스템의 유지보수성과 확장성을 향상시킬 수 있습니다.

바운디드 컨텍스트 맵의 구성 요소는 다음과 같습니다.

1. 바운디드 컨텍스트(Bounded Context): 특정 도메인 모델이 유효한 경계를 정의한 영역입니다. 각 바운디드 컨텍스트는 독립적인 모델을 가지며, 시스템 내에서 명확하게 구분됩니다.

2. 도메인(Domain): 소프트웨어가 해결하려고 하는 문제 영역입니다. 도메인은 비즈니스 로직과 데이터 모델을 포함하며, 바운디드 컨텍스트는 이 도메인을 구현합니다.

3. 컨텍스트 맵(Context Map): 여러 바운디드 컨텍스트 간의 관계를 시각적으로 표현한 맵입니다. 이 맵은 각 컨텍스트의 경계와 그들 사이의 관계를 나타냅니다.

예시로 상품이라는 모델이 존재 할 때, 카탈로그 도메인에서의 상품, 재고 관리 도메인에서의 상품, 주문 도메인에서의 상품은 이름만 같고, 실제로 의미하는 것은 각각 다릅니다. 

회원 도메인에서는 사람을 회원이라 하고, 주문 도메인에서는 주문자, 배송 도메인에서는 보내는 사람이라고 칭합니다. 이렇게, 하위 도메인 마다 사용하는 용어가 다르기 때문에, 올바른 도메인 모델을 개발하기 위해서는 도메인마다 모델을 만들어야 합니다. 또한, 각 모델은 명시적으로 구분되는 경계를 가져서 섞이지 않아야 합니다. 모델은 특정한 컨텍스트(문맥)하에 완전한 의미를 갖는다. 이렇게 구분되는 경계를 갖는 컨텍스트를 DDD에서는 바운디드 컨텍스트라고 부릅니다.

^domain-driven-design-domain
```
"도메인"은 특정 비즈니스, 기술, 활동 영역 또는 이해관계자들의 관심사를 의미합니다. 도메인은 소프트웨어가 해결하고자 하는 문제의 영역이며, 이는 특정 비즈니스 프로세스, 업무 규칙, 정책, 관련 데이터 및 이들 간의 상호작용을 포함합니다.
도메인 개념은 소프트웨어 설계와 개발에 있어 중심적인 역할을 합니다. 도메인 주도 설계에서는 도메인의 깊은 이해를 바탕으로 소프트웨어를 설계하고, 도메인 모델을 통해 비즈니스의 복잡성을 관리하며, 소프트웨어가 비즈니스 요구사항을 정확하게 반영하도록 합니다. 이를 통해 개발자는 비즈니스의 핵심 가치를 제공하고, 유지보수가 용이한 소프트웨어를 만들 수 있습니다.
```

	- '태그' 항목은 특정 주제로 문서를 묶어주기 위하여 적어주는 정보입니다. [[AAC. 바운디드 컨텍스트 맵 (Bounded Context Map)#산출물 양식|산출물 양식]]을 참고하여 기입하여 주십시오.

2. 본문

바운디드 컨텍스트 맵을 작성하기 위해 이벤트 스토밍([Event Storming](https://www.eventstorming.com/)) 기법을 사용합니다. 

[이벤트 스토밍(Event Storming)](https://www.eventstorming.com/)은 이탈리아의 소프트웨어 엔지니어인 [Alberto Brandolini](https://leanpub.com/u/ziobrando)에 의해 개발되었으며, 복잡한 비즈니스 도메인을 이해하고, [도메인 주도 설계(Domain Driven Design. DDD)](https://en.wikipedia.org/wiki/Domain-driven_design)를 적용하기 위한 협업 워크숍 형식의 기법입니다. 이벤트 스토밍은 비즈니스 전문가, 개발자, 사용자 인터페이스 디자이너, 그리고 프로젝트에 관련된 다른 이해관계자들이 함께 모여 비즈니스 프로세스를 탐색하고 모델링하는 데 사용됩니다. 이벤트 스토밍은 바운디드 컨텍스트 맵을 만들기 위해 매우 적합한 설계 기법입니다. 이벤트 스토밍 과정을 통해 이해관계자들의 참여와 협업이 자연스럽게 일어나게 되며, 도메인의 경계를 식별하고 도메인 모델을 보여주는 바운디드 컨텍스트 맵을 만들 수 있습니다.



```
구성요소

- 액터 (Actor) 
	노란색. 사용자 또는 조직, 역할을 담당하는 자를 의미. 추상적인 네이밍이 아닌 비즈니스를 실제로 수행하는 구체적인 역할에 따라 도출해야 한다. 예를 들어, "판매자", "구매자", "상담원", "시스템" 등이 있을 수 있습니다. 

- 정보 (Information)
	연한 녹색. 커맨드를 수행함에 있어 결정 근거가 되는 데이터들을 의미. 예를 들어 상품 목록 조회의 경우 상품 이름/상품 가격/상품 이미지/가격 등이 정보가 될 수 있습니다.

- 커맨드 (Command)
	파란색. 시스템 내에서 일어나는 일. 도메인 이벤트가 발생하는 원인입니다. 예를 들어, "주문 접수", "구매자에게 상품 배송"과 같은 명령이 있을 수 있습니다.

- 도메인 이벤트 (Domain Event)
	오렌지색. 도메인 전문가가 관심이 있는 어떤 사건. 도메인 전문가는 특정 업무 또는 영역에 전문성을 가지고 있는 사람을 의미. 도메인 이벤트는 특정 업무 또는 영역에서 상태가 변경되었다는 것을 의미하며 과거 시제로 기술됩니다.예를 들어, "주문이 접수되었다", "상품이 배송되었다"과 같은 이벤트가 있을 수 있습니다.

- 애그리게이트 (Aggregate/Business Rule)
	연한 노란색. 도메인 이벤트를 처리하며 업무 규칙을 준수하여 시스템이 기대하는 결과를 도출하고 일관성을 유지하는 단위. 커맨드와 도메인 이벤트가 영향을 주는 요소로 추후 도메인의 실제 개념을 표현하는 객체인 엔티티가 됩니다. 애그리거트를 도입함으로써 복잡한 도메인 객체들 사이의 관계를 한눈에 파악할 수 있으며 하나의 맥락에서 지켜져야하는 제약사항을 관리할 수 있게 됩니다. 이러한 과정을 통해 다음 단계인 바운디드 컨텍스트를 쉽게 도출해 낼 수 있습니다.

- 바운디드 컨텍스트 (Bounded Context)
	검은색 경계선. 단계를 걸쳐서 도출했던 도메인 이벤트, 커맨드, 액터, 애그리거트를 모두 고려하여 식별된 모델의 경계를 의미. 도출된 결과물을 연관있는 것끼리 그룹핑하여 각 그룹마다 가지는 명확한 경계를 바운디드 컨텍스트라고 합니다.

- 정책 (Policy)
	회색. 도메인 이벤트가 처리 될 때 준수되어야 하는 업무 규칙. 도메인 이벤트와 커맨드 사이에 위치합니다.

- 시스템 (System)
	분홍색. 외부 시스템부터 일부 레거시 및 마이크로서비스에 이르기까지 책임을 전가할 수 있는 모든 것입니다.

- 핫 스폿 (Hot Spot)
	보라색. 발생한 갈등을 시각화하고 표현하는데 사용. 당장 토론하지 않는다. 나중에 문제가 해결되면 제거합니다.
```



이벤트 스토밍은 다음과 같은 주요 단계로 진행됩니다:

1. **준비**: 넓은 벽이나 테이블 위에 큰 종이 롤을 펼치고, 다양한 색상의 포스트잇과 마커를 준비합니다. 참가자들은 이벤트 스토밍의 목적과 규칙에 대해 안내를 받습니다.

![[doc/_files/event storming 01.png]]

![[doc/_files/event storming 02.png]]

```
왜 포스트잇인가?

- 가능한 가장 간단한 표기법을 사용하면 회의실에 있는 모든 사람이 적극적으로 참여할 수 있습니다. 
- 떼어 내고 붙이기가 쉽기 때문에 이동이 가능하며, 틀린 경우에도 뗄 수 있어 부담을 줄일 수 있습니다.
- 구현 코드보다 포스트잇을 변경하는 것이 훨씬 저렴합니다.
- 온라인 협업툴을 사용하여도 좋습니다. (추천 : Miro - https://miro.com/miroverse/event-storming/)
```


2. **도메인 이벤트 식별**: 참가자들은 비즈니스 프로세스에서 발생하는 중요한 사건(도메인 이벤트)을 포스트잇에 적어 종이 롤에 붙입니다. 이벤트는 과거 시제로 기술되며, "주문이 접수되었다", "결제가 완료되었다"와 같이 표현됩니다.

![[doc/_files/event storming 03.png]]

```
- 각자가 알고 있는 도메인 이벤트를 작성하도록 요청합니다.
- 각자가 작성한 이벤트는 볼 수 있지만, 토론을 시작하지 말고 자신이 옳다고 생각하는 방식으로 기록합니다.
```


3. **시간 순서 정렬**: 이벤트들은 시간 순서대로 배열하여 프로세스의 흐름을 나타냅니다.

![[doc/_files/event storming 04.png]]

```
- 모든 도메인 이벤트를 올바른 타임라인으로 정렬하고 실제로 중복 되는 이벤트를 제거합니다.
- 시간은 왼쪽에서 오른쪽으로 흐르고, 위에서 아래로 동시성을 표현할 수 있습니다.
```


4. **갈등 표현**: 작성 과정에서 생각나는 고민 되는 사항, 상충되는 문제에 대해 표현합니다. 

![[doc/_files/event storming 05.png]]

```
- 고려 사항, 문제점을 도출하고 시각화합니다.
- 당장 문제점을 해결하지 않습니다. 도출과 시각화에 집중하며 추후 논의를 통해 해결하는 과정을 거칩니다.
- 나중에 문제가 해결되면 제거합니다.
```


6. **집단 지성 활용. 집중적인 협업**: 참가자들은 자유롭게 이벤트를 추가하고, 순서를 조정하며, 논의를 통해 비즈니스 프로세스를 명확히 합니다. 이벤트 스토밍은 짧은 시간 동안 집중적으로 진행되며, 참가자들은 서로의 아이디어를 공유하고, 서로의 관점을 이해하며, 공통된 모델을 만들어 갑니다.

![[doc/_files/event storming 06.png]]


7. **추가 모델링 요소**: 이벤트 외에도 명령/동작, 애그리게이트/업무 규칙, 바운디드 컨텍스트(모델 경계), 정책, 시스템 등을 포스트잇으로 표현하여 대상 시스템의 다른 측면을 모델링합니다.

![[doc/_files/event storming 07.png]]


9. **결과물 정리**: 워크숍이 끝난 후, 생성된 모델은 문서화 되고, 참가자들 간의 합의된 내용을 바탕으로 시스템 설계나 개발 작업이 진행됩니다.
