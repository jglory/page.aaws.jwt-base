소프트웨어 형상 관리(Software Configuration Management, SCM)는 소프트웨어 개발 과정에서 소스 코드, 문서, 설정, 데이터 등의 변경 사항을 관리하고 추적하는 일련의 활동을 포함합니다. SCM의 주요 목적은 소프트웨어의 무결성과 추적 가능성을 유지하는 것입니다.

SCM은 일반적으로 다음과 같은 활동을 포함합니다:

  소스 관리
1. 버전 관리(Version Control): 소스 코드의 변경 사항을 추적하고, 이전 버전으로 롤백할 수 있는 기능을 제공합니다.
    
2. 변경 관리(Change Management): 변경 요청을 추적하고, 변경 사항을 승인하며, 변경이 소프트웨어에 적용되는 과정을 관리합니다.


  배포 관리
1. 빌드 관리(Build Management): 소스 코드를 실행 가능한 소프트웨어로 변환하는 빌드 프로세스를 관리합니다.
    
2. 릴리스 관리(Release Management): 소프트웨어의 새로운 버전을 준비하고, 배포하는 과정을 관리합니다.
    
3. 배포 관리(Deployment Management): 소프트웨어를 사용자나 운영 환경에 배포하는 활동을 포함합니다.
    

배포 과정은 SCM의 중요한 부분으로 간주됩니다. 배포 관리는 소프트웨어가 개발 환경에서 테스트, 스테이징, 그리고 프로덕션 환경으로 옮겨지는 과정을 포함하며, 이 과정에서 소프트웨어의 버전을 정확하게 관리하고, 배포된 소프트웨어의 무결성을 보장하는 것이 중요합니다.

현대적인 소프트웨어 개발에서는 DevOps와 같은 접근 방식이 SCM을 확장하여 개발(Development)과 운영(Operations)의 경계를 허물고, 지속적 통합(Continuous Integration), 지속적 배포(Continuous Deployment), 그리고 지속적 전달(Continuous Delivery)과 같은 자동화된 프로세스를 통해 소프트웨어의 빠른 반복과 효율적인 배포를 지원합니다.

자사는 형상 관리툴로 GIT을 사용합니다. 하기의 내용은 자사의 GIT을 통한 소프트웨어 형상 관리 방법 및 정책을 설명하고 있습니다.
<br>


```
Git은 분산 버전 관리 시스템(Distributed Version Control System, DVCS)으로, 소프트웨어 개발에서 소스 코드의 변경 사항을 추적하고 여러 명의 개발자가 협업할 때 사용됩니다. 리누스 토르발스에 의해 2005년에 개발되었으며, Linux 커널 개발을 위한 도구로서 시작되었습니다.

Git의 주요 특징은 다음과 같습니다:

1. 분산 버전 관리: Git은 중앙 서버에 의존하지 않고 각 개발자의 로컬 컴퓨터에 전체 저장소의 복사본을 보관합니다. 이는 네트워크에 접근할 수 없는 상황에서도 작업을 계속할 수 있게 해주며, 중앙 서버에 문제가 생겨도 데이터 손실의 위험이 적습니다.
    
2. 빠른 성능: Git은 대부분의 작업을 로컬에서 수행하기 때문에 매우 빠른 성능을 제공합니다. 또한, Git은 파일의 스냅샷을 저장하는 방식으로 설계되어 있어, 파일의 크기나 프로젝트의 크기에 관계없이 빠른 작업이 가능합니다.
    
3. 데이터 무결성: Git은 SHA-1 해시를 사용하여 파일과 커밋(commit)의 무결성을 보장합니다. 이는 데이터가 손상되거나 변경되었을 때 쉽게 감지할 수 있게 해줍니다.
    
4. 브랜치와 병합: Git은 브랜치(branch)를 쉽게 만들고 관리할 수 있게 해줍니다. 개발자는 기능 개발, 버그 수정, 실험 등을 위해 별도의 브랜치를 만들고, 작업이 완료되면 이를 메인 브랜치에 병합(merge)할 수 있습니다.
    
5. 유연한 워크플로: Git은 다양한 워크플로를 지원합니다. 예를 들어, 중앙 집중식 워크플로, 피처 브랜치 워크플로, Gitflow 워크플로, 포크 및 풀 리퀘스트 워크플로 등이 있습니다.

Git은 오픈 소스이며, GitHub, GitLab, Bitbucket과 같은 원격 저장소 호스팅 서비스와 함께 사용되어 전 세계적으로 널리 사용되고 있습니다.
```

## 소스 형상 관리

소스 관리(버전 관리)을 위한 주요 활동과 처리 과정을 설명합니다.  소스 관리(버전 관리)는 소프트웨어 개발 과정에서 소스 코드의 변경 사항을 추적하고 기록하는 활동으로, 개발자들이 협업하며 코드의 이력과 버전을 관리할 수 있게 해줍니다. 이를 통해 코드의 변경 내역을 안전하게 저장하고, 필요 시 이전 상태로 복원할 수 있으며, 다양한 브랜치에서 동시에 작업을 진행할 수 있습니다.

주요 활동은 다음과 같습니다. 

1. 소스 코드 저장: 소스 코드를 안전하게 저장하고 관리하는 중앙 저장소(또는 분산 저장소)의 설정과 유지 보수.
    
2. 버전 추적: 소스 코드의 변경 사항을 추적하고, 각 변경 사항에 대한 메타데이터(예: 작성자, 날짜, 변경 내용 설명)를 기록.
    
3. 변경 사항 커밋: 개발자가 작업한 변경 사항을 로컬 저장소에 커밋(commit)하고, 이를 중앙 저장소에 푸시(push)하여 다른 개발자와 공유.
    
4. 브랜치 관리: 기능 개발, 버그 수정, 실험 등을 위해 별도의 작업 흐름을 만들고 관리하는 브랜치(branch)의 생성과 병합(merge).
    
5. 병합 충돌 해결: 여러 개발자가 동일한 코드 부분을 동시에 수정했을 때 발생하는 병합 충돌(merge conflict)을 해결.
    
6. 코드 리뷰: 다른 개발자가 작성한 코드를 검토하고 피드백을 제공하는 과정을 지원.
    
7. 태그 및 릴리스 관리: 소프트웨어의 특정 버전을 태그(tag)하여 식별하고, 릴리스(release)를 관리.
    
8. 이력 조회: 소스 코드의 변경 이력을 조회하고, 특정 시점의 상태로 되돌리는(rollback) 기능.
    
9. 보안 및 권한 관리: 저장소에 대한 접근 권한을 관리하고, 민감한 데이터를 보호.
    
10. 백업 및 복구: 소스 코드의 안전한 백업을 수행하고, 필요한 경우 복구.

#### &nbsp;&nbsp;&nbsp;&nbsp;코드 병합

코드 병합 방식과 사례 별 지정된 코드 병합 방식을 설명합니다.

#### &nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;방식

사용되는 코드 병합 방식은 다음과 같습니다. 

1. Merge
	일반적으로 많이 사용되는 병합이며, 커밋 이력을 모두 남길 때 사용한다.
	
2. Squash & Merge
	Squash는 여러 개의 커밋을 하나의 커밋으로 합치는 것을 의미한다.  Squash & Merge는 병합 할 브랜치의 모든 커밋을 하나의 커밋으로 squash한 새로운 커밋을 base 브랜치에 추가하는 방식으로 병합하는 것을 의미한다.
	
3. Rebase & Merge
	rebase(base를 다시 설정) 후 merge 병합. 커밋 히스토리를 동일하게 가져가기 위해 사용한다.
<br>

코드 병합을 할 때 사례 별로 적용하여야 하는 병합 방식은 다음과 같습니다.

##### &nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;FEATURE -> DEV
	merge 한다

##### &nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;FEATURE -> QA
	merge 한다

##### &nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;FEATURE -> STG
	squash & merge 한다

##### &nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;STG -> MASTER
	merge 한다

#### &nbsp;&nbsp;&nbsp;&nbsp;코드 롤백

사용되는 코드 롤백 방식과 처리 과정을 설명합니다.


##### &nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;방식

사용되는 롤백 방식은 다음과 같습니다. 

1. checkout
2. reset
3. revert


##### &nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;처리

코드를 롤백하는 과정은 다음과 같습니다. 커밋 해쉬값으로 commit-hash 값을 가지는 코드를 롤백하는 것을 사례로 과정을 설명하였습니다.

```
commit-hash : 롤백할 코드의 커밋 해쉬값
```


1. master 코드를 롤백합니다.
```
$ git checkout master
$ git revert --no-commit {{commit-hash}}
$ git commit -m "revert 한 이유"
$ git push
$ git checkout stg
$ git rebase master
```
	
2. stg 코드를 롤백합니다.
```
$ git checkout stg
$ git revert --no-commit {{commit-hash}}
$ git commit -m "revert 한 이유"
$ git push
$ git checkout master
$ git merge stg
```

3.  qa 코드를 롤백합니다.
```
$ git checkout qa
$ git revert --no-commit {{commit-hash}}
$ git commit -m "revert 한 이유"
$ git push
```

## 문서 산출물 관리

개발 산출물은 소프트웨어 개발 과정에서 생성되는 모든 결과물을 포함합니다. 소스 코드는 이 중 하나에 불과하며, 소스 코드 이외의 산출물들 또한 개발 프로세스에 따른 공정의 최종적인 기대 결과물로 소스 코드와 동일하게 관리되어야 합니다. 

문서 산출물 관리에는 [Docs as Code](https://medium.com/@Danpatpang/docs-as-code-298802a691d1) 문서 관리 기법을 적용합니다. 이 개념은 문서 작성, 관리, 배포에 소프트웨어 개발에서 사용되는 도구와 기술을 적용하는 것을 의미합니다. 문서를 버전 관리 시스템에 저장하고 코드 리뷰, 자동화된 테스트, 지속적 통합(CI), 지속적 배포(CD) 등의 소프트웨어 개발 공정을 문서에 적용합니다. 이 방식은 특히 기술 문서에 유용하며, 개발자들이 코드와 함께 문서도 쉽게 관리하고 업데이트할 수 있도록 합니다.

이는 특히 Agile 개발 환경과 DevOps 문화에서 잘 맞는 접근 방식입니다. 최근 Docker, Github 등의 다양한 서비스에서 서비스에 대한 문서를 [Docs as Code](https://medium.com/@Danpatpang/docs-as-code-298802a691d1)로 관리하고 있습니다.

상기 산출물들을 소스 코드와 함께 특정 디렉토리를 지정하여 저장하여 소스 코드와 함께 형상 관리가 이루어지도록 합니다.  문서 산출물 디렉토리는 다음의 정책을 적용합니다.

###### &nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;문서 산출물 디렉토리

먼저 문서 산출물 관리 루트 디렉토리를 정하도록 합니다. 루트 디렉토리는 다음 조건을 기준으로 프로젝트의 상황에 맞게 정하도록 합니다. 

- 소스와 함께 형상 관리(버전 관리) 가능한 디렉토리
- 문서 관리 디렉토리 명은 {{프로젝트}}-doc

예를 들어, 단일 프로젝트 폴더 내에 모든 소스가 있다면 문서 산출물 관리 루트 디렉토리는 다음과 같습니다.

```
{{프로젝트}}/dev-docs

프로젝트 : 프로젝트의 코드가 존재하는 루트 폴더명
```


다음은 개별 문서 산출물의 루트 디렉토리입니다. 

```
dev-docs
├── A 분석
│   ├── A 업무 분석
│   │   ├── B 보편 언어
│   │   └── C 바운디드 컨텍스트 맵
│   └── B 아키텍쳐 분석
│       ├── A 현행 소프트웨어 아키텍쳐 구성도
│       ├── B 현행 시스템 아키텍쳐 구성도
│       └── C 현행 테이블 관계도
├── B 설계
│   ├── A 아키텍쳐 설계
│   │   ├── A 소프트웨어 아키텍쳐 구성도
│   │   └── B 시스템 아키텍쳐 구성도
│   ├── B 애플리케이션 설계
│   │   ├── B 클래스 명세서
│   │   ├── C 클래스 구조도
│   │   └── E 시스템 처리 흐름도
│   └── C 데이터 설계
│       ├── B 테이블 정의서
│       └── C 테이블 관계도
└── C 구현
    └── A 소프트웨어
        ├── A 소프트웨어 처리 흐름도
        └── B DB 기능 명세서
```

>[!note]
> 개별 문서 산출물 별 문서 관리 방식은 개별 산출물 가이드 문서 내 '작성' 섹션을 확인하세요.

## 배포 관리


### &nbsp;&nbsp;코드 배포

다음은 단계 별 코드 배포 절차를 설명하고 있습니다.

```
파트 리더 : 개발 결과물을 검토하고 QA에 대한 배포 승인 및 배포 권한을 가진 자. Part Leader(PL)
프로젝트 관리자 : 개발 결과물을 검토하고 STG에 대한 배포 승인 및 배포 권한을 가진 자. Project Manager(PM)
배포 담당자 : 배포 대상 결과물에 대해 PRD(실 운영) 배포 권한을 가진 자. Distribution Manager(DM)
```

```
코드 반영 요청 : Pull Request(PR)
```
<br>

#### &nbsp;&nbsp;&nbsp;&nbsp;FEATURE
- 개발 담당자는 개발 항목(이슈)을 할당받습니다.
- master 브랜치에서 개발 항목의 업무번호를 기반으로 feature 브랜치를 분기합니다.
- 개발을 진행합니다.

#### &nbsp;&nbsp;&nbsp;&nbsp;QA
- 개발 담당자는 QA가 필요한 feature 브랜치의 qa 브랜치 병합과 배포를 요청하는 코드 반영 요청(PR)을 생성합니다.
- 파트 리더(PL)는 코드 반영 요청(PR)을 검토하고 승인을 합니다. 
- 개발 담당자는 승인을 확인하고 코드 병합을 하고 feature 브랜치를  qa 브랜치에 반영합니다. 
- 파트 리더(PL)은 qa 배포를 진행합니다.

#### &nbsp;&nbsp;&nbsp;&nbsp;STG
- 개발 담당자는 qa 통과를 하고 배포 예정이 된 feature 브랜치에 대해 stg 브랜치 병합을 요청하는 코드 반영 요청(PR)을 생성합니다.
- 프로젝트 관리자(PM)은 코드 반영 요청(PR)을 검토하고 승인을 합니다.
- 개발 담당자는 승인을 확인하고 코드 병합을 하고 feature 브랜치를  stg 브랜치에 반영합니다.
- 프로젝트 관리자(PM)은 stg 배포를 진행합니다.

#### &nbsp;&nbsp;&nbsp;&nbsp;MASTER
- 예정된 배포 시점에 운영 배포 담당자(DM)가 stg 브랜치를 master 브랜치에 반영합니다.
- 운영 배포가 이루어집니다.
